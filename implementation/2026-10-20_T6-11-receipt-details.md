- 구현 일시: 2026-10-20
- 기준: D-079 (사용자 결정), `spec/features/receipt-parser.md` §3

## 변경 사항
- DB `029_receipt_details.sql`: `expense_items.paid_time`·`approval_number`·`merchant_address`·`line_items`(서버 함수로만 채움, 직원·관리자 직접 수정 X), 승인번호 인덱스, `apply_receipt_parse`가 네 값을 검사해 빈 칸에만 저장(품목 최대 50줄·이름 100자·빈 이름 제외, 시각·승인번호 형식 검사), `claim_duplicate_receipts(claim_id)`(같은 회사 안 중복 — 내 것은 제목, 다른 직원 것은 건수만)
- 테스트 `015_receipt_details.sql`: 저장·형식 검사, 직접 수정 불가, 내 중복(제목 보임), 같은 회사 다른 직원(건수만·제목 안 보임, 승인번호 없이 사업자번호+시각으로도 판별), 다른 회사는 세지 않음·조회 불가
- AI: 요청 스키마·안내 문구에 네 값 추가, `normalizeParsed`로 재검사(단위 테스트)
- 화면: 항목 편집 맨 위 중복 경고(막지 않음), 접힌 "AI가 읽은 참고 정보"(시각·승인번호·주소·품목 표, 할인은 빨간 음수), 소명서 영수증 목록에 "중복 의심" 배지

## 특이 사항
- 실측(같은 영수증, AI 처리 시간): 네 값 모두 정확(12:41, 30012345, 주소, 품목 3줄). 처음엔 적혀 있지 않은 단가를 나눠서 채워 "적혀 있을 때만"으로 안내를 고침 → 단가 비움 확인
- 시간: 실행마다 첫 요청 3.3~4.9초, 이어지는 요청 1.7~1.9초(이전 1.6~1.9초). 첫 요청이 느린 원인은 연결 준비로 보이며 화면 체감(RUM: employee.receipt_upload_one)으로 계속 지켜본다
- 관리자 승인 화면 표시는 T9에서
