# [Spec] 성능·확장 규칙 (D-073)

회사·직원·영수증이 늘어나도 화면이 답답하지 않도록 지키는 규칙. 데이터베이스 격리·RLS 성능 규칙은 CLAUDE.md 제2장 제4조, 화면 규칙은 `ui-rules.md`.

## 1. 영수증 이미지 — 용도별로 한 장씩
| 용도 | 파일 | 크기 기준 | 쓰는 곳 |
|---|---|---|---|
| **보관본(원본)** | `{item_id}.jpg` (PDF는 원본 그대로) | 긴 변 **2000px**, JPEG 품질 약 0.85 (장당 약 0.3~0.6MB) | 세무 마감 ZIP, 확대 보기, AI 영수증 인식 |
| **썸네일** | `{item_id}_thumb.webp` (WebP를 못 만드는 구형 브라우저는 `_thumb.jpg`) | 긴 변 **320px**, WebP (장당 약 15~25KB) | 모든 목록·표의 작은 사진 |

- **정책(사용자 확정)**: 휴대폰 원본(보통 4000px·3~5MB)은 보관하지 않고 **2000px 보관본만** 저장한다. 세무사 ZIP도 이 보관본을 넘긴다.
- 두 파일 모두 **업로드 전에 휴대폰(브라우저)에서 만든다**. 서버 이미지 변환 비용이 없다.
- PDF 영수증은 축소하지 않고 원본 그대로 보관한다. 썸네일은 PDF 아이콘으로 대신한다(브라우저에서 PDF를 그리는 라이브러리는 무거워서 쓰지 않는다).
- 목록·표에는 **썸네일만** 보여 주고, 눌렀을 때만 보관본을 불러온다.
- 실측(2026-10-17, 4032×3024급 사진): 1.47MB → 보관본 445KB(1500×2000 JPEG) + 썸네일 26KB(240×320 WebP), 처리 0.1초(Chromium)·0.3초(iPhone Safari 엔진). 다시 그리면서 위치정보(EXIF)가 지워진다.
- 2000px는 일반 영수증(가로 80mm·세로 200mm 안팎) 기준 약 250dpi로, 문서 스캔 권장 수준(200~300dpi)에 해당한다. 전자 보관 요건은 세무사무소 확인 질문(`tax-upload-format.md` §4)에 포함한다.
- 경로: `receipts/{company_id}/{member_id}/{claim_id}/{item_id}.jpg`, 썸네일은 같은 폴더(같은 접근 규칙, `schema.md` §4).

## 2. AI 영수증 인식에 보낼 화질
- **보관본(2000px)을 그대로 보낸다.** 작은 글씨(사업자번호·공급가액·부가세)를 정확히 읽는 것이 비용 차이보다 중요하다.
- 참고(Gemini 기준): 이미지는 768×768 조각마다 258토큰. 1000×2000 영수증 ≈ 6조각 ≈ 1,500토큰, 768×1536로 줄이면 ≈ 2조각 ≈ 500토큰. Flash 계열 입력 단가로 장당 **1원 미만** 차이라 화질을 낮춰 아낄 실익이 없다(크레딧 1장 판매가 대비 무시 가능).
- 썸네일은 인식에 쓰지 않는다.

## 3. 목록은 나눠서 불러오기
- 소명서·영수증·정산·알림 이력 목록은 **기본 = 이번 달**(또는 화면의 기본 필터), **[더 보기]로 50건씩** 추가로 불러온다.
- **날짜(date) 컬럼은 `YYYY-MM-DD` 문자열과 비교한다**(`src/lib/dates.ts`, 한국 시간 기준). timestamp와 비교하면 인덱스의 날짜 부분을 못 써서 회사 전체 행을 훑는다(벤치에서 16ms → 2ms 확인).
- 방식: 정렬 키(예: `submitted_at desc, id desc`) 기준으로 "마지막 항목 다음부터" 불러오는 커서 방식(건너뛰기 offset 방식은 쓰지 않는다). 기존 `(company_id, …)` 인덱스를 그대로 탄다.
- 합계·건수는 목록과 따로 서버에서 계산해 보여 준다(불러온 건만 더하지 않는다).
- 멤버·부서처럼 회사당 수십 건인 목록은 한 번에 불러온다.

## 4. 사진 보기 링크는 한 번에 받기
- 비공개 버킷이라 사진은 시간 제한 링크(signed URL, 10분)로만 보인다.
- 한 화면에 필요한 링크는 **한 번의 요청으로 묶어서** 받는다(`createSignedUrls`). 사진마다 따로 요청하지 않는다.
- 같은 화면을 다시 그릴 때는 유효 시간 안의 링크를 다시 쓴다.

## 5. 세무 마감 ZIP — 브라우저에서 묶기
- 규모 예상: 30인 회사 × 직원당 월 10~20장 = **월 300~600장, 약 100~300MB**.
- 서버 함수는 한 번에 돌려줄 수 있는 크기·시간 제한이 있어(Vercel 함수 응답 약 4.5MB) 서버에서 ZIP을 만들어 내려보내지 않는다.
- **관리자 브라우저가** 엑셀(서버가 만듦)과 영수증 보관본(signed URL로 직접 받음)을 받아 그 자리에서 ZIP으로 묶어 저장한다. 진행률("영수증 120/350장")을 보여 주고, 실패한 장만 다시 받는다.
- 한 파일이 너무 커지면(약 500MB 초과) "PocketExpense_회사_2026-10_1.zip", "_2.zip"처럼 나눠 저장한다.

## 6. 영수증 올리기·AI 인식 동시 처리
- 한 번에 고를 수 있는 영수증은 **최대 10장**. 더 올리려면 한 번 더 고른다(소명서 한 건의 항목 수는 제한하지 않는다).
- 업로드는 동시에 3장씩, AI 인식은 **동시 최대 3건**(`expense-claim-flow.md` Step 2). 끝나는 대로 다음 장을 처리한다.
- AI 인식이 실패하거나 시간 초과면 **자동으로 1번 다시 시도**하고, 그래도 실패하면 "직접 입력 필요"로 둔다(크레딧은 성공한 인식에만 차감 — `receipt-parser.md`).

## 7. 측정
- 데이터베이스: `npm run bench:db` — **회사 200·직원 6,000·소명서 8.4만(1년치)·영수증 25.2만** 기준, 화면에서 쓸 조회 18종(목록 1·2쪽, 이번 달, 결재 대기, 정산 대기, 월 합계, 세무 마감 월 항목, 상세, 사진 권한 확인, 직원 목록·미지급 합계, 검토자 결재함). 기준 50ms.
  - 2026-10-17 결과: 모두 **10ms 이하**(최대 8.3ms — 관리자 목록 1쪽, 그 외 0.2~3.2ms).
  - 실행에 약 1분 40초 걸린다(관리 API 제한이 약 100초라 규모를 더 키우려면 나눠서 넣는다).
  - **벤치 뒤에는 반드시 표를 압축한다**(`--bench`가 자동으로 `vacuum full`). 대량 입력 후 롤백한 행이 남아 무료 요금제 디스크가 가득 찬 사고가 실제로 있었다(736MB → 압축 후 19MB).
- 화면: 직원 목록은 휴대폰(CPU 느리게) 기준 첫 화면 2초 안에 썸네일까지 보이는지 확인한다.

## 8. 요금제
- 저장 공간: Supabase 무료 1GB ≈ 보관본 2,000~3,000장. 세무 증빙은 5년 보관이라 지우지 않는다. **실제 고객을 받기 전에 Pro 요금제로 올린다**(사용자 결정).

## 9. 공용 모듈 (화면에서 이걸 쓴다)
| 모듈 | 하는 일 |
|---|---|
| `src/lib/receipts/image.ts` | 브라우저에서 보관본(2000px JPEG)·썸네일(320px WebP, 안 되면 JPEG) 만들기, PDF는 그대로 |
| `src/lib/receipts/paths.ts` | 저장 경로(첫 폴더 = 회사 id) |
| `src/lib/concurrency.ts` | 동시 N건 처리 + 실패 시 재시도 + 진행률 콜백 (업로드·AI 인식 동시 3건, 재시도 1회) |
| `src/lib/storage/signed-urls.ts` | 화면당 사진 링크 한 번에 발급(서버 전용, 10분) |
| `src/lib/pagination.ts` | 커서 만들기·풀기, 조건식(`.or`), limit+1로 다음 쪽 판단 (서버 전용) |
| `src/lib/dates.ts` | 한국 시간 오늘·이번 달, 월 범위(`YYYY-MM-DD`) |
- DB: `expense_items.receipt_thumb_path`(migration 021), 저장소 열람 정책은 보관본·썸네일 모두 "항목에 등록된 파일 + 그 소명서를 볼 수 있는 사람"만(`supabase/tests/009_receipt_thumbnails.sql`). 경로 컬럼은 서버 함수로만 기록한다.
